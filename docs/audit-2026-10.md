# Full audit — October 2026

- Date: 2026-10-07
- Scope: conformance with [clig.dev](https://clig.dev/) and with the project's own ADRs (above all ADR 0013, "a difference from the reference is a defect unless it is on this list"), parity with KCC 12.0.0, behaviour on hostile or odd input, the machine contract (protocol v1), dependencies, supply chain and release, and documentation and tests against the code.
- Snapshot: 53 commits, 14 ADRs, `main` at `5c384f4` (PR #9), release `v0.7.2` (published 2026-10-03). About 12,700 lines of Rust in two crates, 274 tests.
- Method: a read of the command line (`crates/mangapress-cli/src`, all of `main.rs`, `protocol.rs`), of the archive readers, of `.github/`, both installers, the README, the protocol document, ADR 0009 and ADR 0013. Then the binary built from `HEAD` (and the published musl archive of `v0.7.2`, whose SHA-256 matches `checksums.txt`) was run against fixtures made for this audit (about 250 runs, the commands listed under each finding), and these tools were run: `cargo fmt --check`, `cargo clippy -D warnings` (and a stricter pass for `unwrap`, `expect` and `panic` in non-test code), `cargo test --workspace`, `cargo audit`, `cargo metadata` for the license of every locked crate, and `tools/parity/parity.py` against KCC `v12.0.0` — first as shipped (Kindle 11, the whole matrix), then again with the profile replaced by 23 others (a few scenarios each). Everything was run on Linux. The fixtures and scripts were not kept; the commands are in the findings. Nothing in the repository was changed except this file (the parity script was copied with its `PROFILE` line edited, and the copies were deleted).

This is a report, not a plan. It names what is wrong, where, and what the direction is; deciding what becomes a pull request, and in what order, is a separate step.

**How findings are classified.** *Defect*: the behaviour contradicts the project's own ADR, README or protocol document. *Gap*: a clig.dev item or a risk that the ADRs neither adopted nor declined. *Reconsider*: something an ADR decided whose premise has since changed. Priority is High, Medium or Low; effort is S (a few lines and a test), M (one focused pull request) or L (a design question first).

**What was not read or run.** ADRs 0001–0008, 0010–0012 and 0014 were not read in full. The image-processing modules (`crop`, `contrast`, `resample`, `quantize`, `rainbow`, `webtoon`) were not read line by line: they are checked by parity (below) rather than by reading, and by 138 runs over degenerate sizes. The EPUB writer was read only where it names files and escapes text. Windows and macOS behaviour was not run: reserved Windows names, trailing dots and spaces were reasoned about, not tried. `cargo-llvm-cov` needs `llvm-tools`, which this toolchain does not ship, so coverage was not measured. The installers were read, not executed. Parity ran on a drawn corpus, not on real scans, and not on a Kobo-named EPUB (the Kobo EPUB package is pinned by unit tests, which were not re-derived).

## What is already working well

- **Parity with KCC 12.0.0 holds where it is checked.** `tools/parity/parity.py` as shipped passed all 409 checks (Kindle 11, 41 scenarios: spreads in every splitter mode, cropping, inter-panel crop, auto-level, gamma, stretch, wallpaper, rainbow eraser, colour output, CBZ borders, three dithers compared pixel for pixel, webtoon cuts compared exactly). The same scenarios on other devices are reported under finding 7.
- **The command line is the best part of the project against clig.dev.** `-h`/`--help` go to stdout and exit 0; no arguments, a stray argument and an unknown flag exit 2 with a one-line message; flags may come in any order (clap); an unknown profile gets "did you mean"; routine progress is on stderr, with a live page counter on a terminal and one line per chapter otherwise; `--quiet` keeps warnings; `--dry-run`, `--list-profiles`, `--version` all exist; the machine mode is opt-in and leaves the terminal mode alone.
- **Static analysis and tests are clean.** `cargo fmt --check` and `cargo clippy --workspace --all-targets -D warnings` report nothing; 274 tests pass; there is no `unsafe` anywhere in the code. In non-test code there are 8 `expect` calls, every one on an internal invariant (a buffer sized by construction, a value just inserted, an argument clap already required); none is reachable from an input.
- **Hostile text is handled.** A `ComicInfo.xml` with a DTD (an entity-expansion bomb) is refused at once with a message; titles and chapter names full of `<`, `&`, `]]>` and quotes produced an EPUB in which every XML part is well-formed and the metadata is escaped; entry names such as `../../evil.png`, `/abs.png`, `a\b.png` and `CON.png` become chapters named by position, so nothing from the input chooses a path inside the book or on disk.
- **Degenerate sizes do not crash it.** 138 runs over pages of 1×1, 2×2, 1×3000, 3000×1, 7×5, 3×5000, 5000×3 and others, crossed with 15 option sets (upscale, stretch, both splitter modes, webtoon, rainbow eraser, no processing, wallpaper, inter-panel crop, forced colour, PDF, custom 1×1 and 3×7 resolutions), produced no panic, abort or signal.
- **Output is reproducible where it matters.** Two runs of the same conversion give byte-identical pages; the only differences are the modification times the `zip` crate stamps on each entry and the EPUB's required `dcterms:modified`. The musl release and a glibc build also give byte-identical pages (180 of 180).
- **A sensible memory model for ordinary books.** A 127 MiB, 180-page volume converted in 13 s using a peak of 508 MiB (about four times the input).
- **The license posture is clean.** All 285 locked crates are permissive (MIT, Apache-2.0, BSD, Zlib, ISC, Unlicense, CC0); the only crate that mentions a GPL-family license (`r-efi`) offers it as one of three choices (`MIT OR Apache-2.0 OR LGPL-2.1-or-later`). The GPLv3 boundary of ADR 0007 is intact. `cargo audit` reports no vulnerability.
- **The machine contract matches its document** except for the one code in finding 15. With `--json-events`, stdout was JSON Lines only on every run tried; `invalid_arguments` is a structured event even when clap rejects the line; a closed pipe is reported as `event_write_failed`, not a panic.
- **The release is reproducible in intent:** `--locked` in the release workflow, the licenses and the notices travel in each archive, the checksums match.

## Findings — behaviour and safety

### 1. A ZIP entry that lies about its size aborts the process, and says nothing in machine mode

**Class:** defect (protocol document: an `error` event is "fatal issue with stable code"; ADR 0011). **Priority:** Medium. **Effort:** S.

**Where:** `crates/mangapress-core/src/archive/cbz.rs:34`: `Vec::with_capacity(zip_entry.size() as usize)`, where the size is whatever the central directory of the downloaded archive says.

**Evidence:** a ZIP64 archive whose central directory declares an entry of 2^62 bytes (and holds 4 kB of real data):

```
$ mangapress forged.cbz --profile KPW5 --format cbz -o out.cbz
memory allocation of 4611686018427387904 bytes failed          -> SIGABRT
$ mangapress forged.cbz ... --json-events
{"stage":"inspect","state":"started",...}                      -> SIGABRT, no error event, nothing else on stdout
```

**Why it matters:** it is the first thing the program does with an input it did not make, so any `.cbz` from anywhere can end it without a message a consumer can read. mangabound, which branches on the `error` event's `code`, gets an abnormal exit with no event.

**Direction:** do not allocate from the declared size (`Vec::new()`, or capacity capped at a few MiB), and read through `take()` with the limit of finding 2.

### 2. Nothing bounds what an input can cost

**Class:** defect against ADR 0013 for the image size (KCC refuses, mangapress does not, and it is not on the list of differences), gap for the rest. **Priority:** Medium. **Effort:** M.

**Where:** `archive/cbz.rs:33-35` reads every non-directory entry whole before anything looks at its name; the extension filter is `main.rs:726` (`filter_image_entries`), after the read. Image decoding uses the `image` crate's default 512 MiB allocation limit and no pixel limit.

**Evidence:**

```
notes.txt of 400 MiB of zeros inside a 408 kB .cbz                     -> converts, peak RSS 405 MiB for a file that is then dropped
one 20000×20000 PNG (400 megapixels, 439 kB on disk), 6 GB cap         -> converts in 52.8 s, peak RSS 4,565 MiB
one 60000×60000 PNG (3.6 gigapixels, 3.7 MB)                           -> "Memory limit exceeded", a clean error
```

Pillow, which KCC uses, raises `DecompressionBombError` above twice `Image.MAX_IMAGE_PIXELS` (89,478,485), that is above 178,956,970 pixels, and KCC never sets that constant (it appears nowhere in `kindlecomicconverter/`), so KCC refuses the 400-megapixel page and mangapress converts it. Pages are decoded in parallel (`process_chapter_pages`), so a book of eight such pages would ask for about 36 GB (not run: it would take this machine down).

**Direction:** decide whether a name can be refused before its bytes are read (skip non-image entries by name, as the filter already does, but before `read_to_end`); give each entry a ceiling on its uncompressed size; refuse pages above Pillow's limit with a message, or put the difference in ADR 0013's table with the reason. Both ceilings should be generous (a page of a comic is never 256 MiB).

### 3. The output is written in one non-atomic call, and ADR 0009's "nothing to clean up" is true only for a new file

**Class:** reconsider (ADR 0009 declined Ctrl-C handling because "no output file exists yet at that point"). **Priority:** Medium. **Effort:** S.

**Where:** `crates/mangapress-cli/src/main.rs:1504`: `std::fs::write(&output_path, &output_bytes)` truncates the destination and then writes it.

**Evidence:** with an output that already exists, a run that dies during the write (simulated with `ulimit -f`, which kills the process with SIGXFSZ part-way; a Ctrl-C, a power cut or a full disk have the same effect) left the 682,486-byte good book as a 51,200-byte file, with no message.

**Why it matters:** the ADR's measurement (a signal kills it in 7 ms and leaves nothing) was made on a fresh output name. Books are tens to hundreds of megabytes now (the 180-page test volume is 77 MB), the write takes a visible time, and converting again over a previous output is the usual way to try other options.

**Direction:** write to a temporary file beside the destination (`tempfile` is already a dev-dependency), `sync`, rename over the destination, remove the temporary file on error. Add a line to ADR 0009 saying the premise held for new outputs only.

### 4. The default output name differs from KCC's and can overwrite another book

**Class:** defect (ADR 0013; the list of deliberate differences has one entry on output names, and it is the reverse of this). **Priority:** Medium. **Effort:** S to M.

**Where:** `main.rs:984-1017` (the choice of the output path) and `:44-58`, `:82-109` (the collision check, which only looks at the input).

**Evidence (KCC's rule is `getOutputFilename` in `comic2ebook.py`):**

```
folder  "Vol. 1"  ->  "Vol.cbz"         KCC: "Vol. 1.cbz"     (Path::with_extension replaces what follows the last dot)
folder  "Vol. 2"  ->  "Vol.cbz"         a second run overwrote the first, no warning
folder  "Vol 1.5" ->  "Vol 1.cbz"       KCC: "Vol 1.5.cbz"
$ cd "My Manga" && mangapress .    ->   a file named " (mangapress)", without an extension, inside the input folder; the next run reports "skipped 1 non-image file"
two files "CM a.cbz", "CM b.cbz" with the same ComicInfo Series, both with  -o dir   ->  "Chainsaw Man.cbz" written twice; the second replaced the first, no warning
```

KCC derives the name from the source (`srcpath + ext` for a folder, `source_path.stem` for a file into `-o`), and when that path exists it picks `…_kcc0`, `…_kcc1` rather than overwrite it. mangapress derives the name from the resolved title in the `-o dir` case and only renames when the target *is the input*.

**Why it matters:** `Vol. 1`, `Vol. 2` is an ordinary way to name folders and `Series` is the same for every volume of a series; either silently loses a converted volume. A person at a terminal is exposed. mangabound passes an output *folder* and a title (`src/adapters/mangapress/conversion-port.ts:42`), so it is exposed only if two of its books are given the same title, which its own naming of titles is meant to prevent (not re-checked here).

**Direction:** for a folder, append the extension to the whole name; canonicalise `.` and `..` before taking a name; follow KCC's `_kccN` rule for any existing target in the default case (named after this tool, as the existing entry is), and decide whether an explicit `--output file.ext` may overwrite (it does today, which is the usual meaning of an explicit path; if it stays, say so in the ADR). **Decision for the owner:** overwrite on an explicit path or not.

### 5. Output problems are found after the whole conversion, and `--dry-run` approves them

**Class:** defect (`--dry-run`: "Show what would be produced"; the protocol document says it "creates nothing", and nothing in it checks that the output can be created). **Priority:** Medium. **Effort:** S.

**Where:** `main.rs:984-1008` (a path that ends in `.epub`, `.cbz` or `.pdf` is taken literally, its folder never checked) and `:1504` (the first write).

**Evidence:**

```
$ mangapress good.cbz -o out/missing/b.cbz --dry-run     -> "would write: out/missing/b.cbz", exit 0
$ mangapress good.cbz -o out/missing/b.cbz               -> converts every page, then: Error: writing output to out/missing/b.cbz ... No such file or directory
a ComicInfo Series of 300 characters, -o folder          -> converts every page, then: File name too long (os error 36)
-o a read-only folder                                    -> converts every page, then: Permission denied
```

The two forms of `--output` also disagree: a folder that does not exist yet is created (`main.rs:1003`), a file path inside one is not.

**Why it matters:** for a 100 MB book on a slow laptop the wrong path costs minutes. It is the same shape as the plan that promises and the run that fails.

**Direction:** at plan time, check that the output's folder exists or can be created and is writable (without creating anything in dry-run), cap the name at what the file system allows, and create the missing folder for a file path as the folder form already does.

### 6. File names taken from `ComicInfo.xml` are only partly cleaned

**Class:** gap. **Priority:** Low. **Effort:** S.

**Where:** `main.rs:32-34` (`sanitize_filename`) replaces nine characters.

**Evidence:** a `Series` of `..` gives a file named `...cbz`; a `Series` with a newline and a tab gives a file whose name contains them (`a?b^Ic.cbz` under `cat -A`); an empty one falls back to the file name, which is right. Not run, only reasoned: on Windows a title of `CON`, `NUL` or `COM1`, or one ending in a dot or a space, names a device or a file Windows will not keep as written.

**Why it matters:** the title is data from inside a downloaded archive.

**Direction:** drop control characters, trim trailing dots and spaces, prefix the reserved device names, and cut at a length that leaves room for the extension (finding 5).

### 7. Kindle DX: the CBZ page height differs from KCC's, and parity checks only one device

**Class:** defect (ADR 0013) and gap (`tools/parity` README: "Any device but the Kindle 11 profile … is not covered"). **Priority:** Low for the device, Medium for the gap. **Effort:** S.

**Evidence:** running the unmodified `parity.py` with its `PROFILE` replaced by `KDX` and the scenario `CBZ: padded to the screen`:

```
spread_uneven_margins.png: Rotated size       KCC [824, 1200], mangapress [824, 1000]
landscape_nearly_square.png: Normal size       KCC [824, 1200], mangapress [824, 1000]
spread_dark.png: SplitFirst / SplitSecond / Rotated     KCC [824, 1200], mangapress [824, 1000]
```

KCC's `comic2ebook.py:1733` (`# CBZ files on Kindle DX/DXG support higher resolution`) raises the height of the `KDX` profile to 1200 when the format is CBZ; mangapress has the profile's aspect tolerance for it (`resize.rs:26`) but not this. `--format auto` gives CBZ for exactly this device (`main.rs:317`), so the default path hits it.

The same scenarios were then run on 23 other devices: `KS`, `KoLC`, `K34` and `KDX` with six scenarios each (default options, spreads split and rotated, colour output, CBZ padded, no upscale, stretch), and 19 more (`K1`, `K2`, `K57`, `KPW`, `KO`, `KPW6`, `KCS`, the five Scribe sizes `KS1860`, `KS1920`, `KS1240`, `KS1324` and `KS3`, `KoMT`, `KoG`, `KoAH2O`, `KoF`, `Rmk1`, `RmkPP`, `RmkPPMove`) with two (default options, CBZ padded). Of those 62 device-and-scenario runs, 61 matched KCC and this is the one that did not.

**Why it matters:** the project's central claim is "the same pages". The shipped check passes 409 times and still missed this, because the question it asks is asked on one device. The owner reads on a Kindle 11, which is covered; this is for everyone else.

**Direction:** the fix is a few lines (the KCC special case) and one parity scenario; the larger change is to let `parity.py` take `--profile` (it is already a constant) and to run a few profiles of different resolution, palette and family on every change that touches pixels, and once on every KCC release. See finding 16.

### 8. `--dry-run` panics on a closed pipe

**Class:** defect (the comment at `main.rs:487-491` states the rule and fixes it for `--list-profiles`). **Priority:** Low. **Effort:** S.

**Where:** `main.rs:1092-1098`: the seven `println!` of the human dry-run summary.

**Evidence:** with the reader of stdout gone (`mangapress book.cbz --dry-run | head -0`): `failed printing to stdout: Broken pipe`, exit 101, and the advice to set `RUST_BACKTRACE`. The `--json-events` forms exit 1 with `writing JSON event: Broken pipe`, and `--list-profiles` exits 0, as intended.

**Direction:** write through `writeln!` and stop quietly, as `--list-profiles` does.

### 9. A folder input follows symbolic links anywhere

**Class:** gap (mangabind's ADR 0014 decided the equivalent question for its input; mangapress's has no record). **Priority:** Low. **Effort:** S, with a decision.

**Where:** `archive/folder.rs:23`: `path.is_dir()` follows links, and `:30` reads whatever a link names.

**Evidence:** a link `c001/p2.png -> /elsewhere/other.png` was read and became page 2 of the book. A link `c001/loop -> ..` ends the run with `Too many levels of symbolic links` (the kernel's limit, not a check).

**Why it matters:** the same reason as ADR 0014: a folder someone else made can put a file of yours into a book you then share. Only files that decode as images become pages (a text file named `.png` fails the run), which limits the harm to images.

**Direction:** **decision for the owner:** apply ADR 0014's rule (follow a link only to a regular file inside the input, otherwise skip it with a `warning`), or record that mangapress reads what it is pointed at. If the rule is applied, the code is the same in both tools.

### 10. A failed page is named in the event but not on the terminal

**Class:** gap. **Priority:** Low. **Effort:** S.

**Where:** `main.rs:1292`: `bail!("processing a page in chapter '{chapter_title}': …")` drops `error.page`, which the machine event carries (`with_page`).

**Evidence:** a book whose second image is cut short fails with `Error: processing a page in chapter 'c001': image decode/encode error: unexpected end of file`, and the event says page 2. KCC also stops the whole run on a corrupt image (`comic2ebook.py:1389`, "Image file … is corrupted"), so the stop is parity; the missing position is not.

**Direction:** put the page number (and, in the folder case, the file name) in the message.

## Findings — dependencies and release

### 11. The dependency tree is larger than the program needs

**Class:** gap. **Priority:** Low to Medium. **Effort:** S.

**Evidence:**

- `imageproc` (`crates/mangapress-core/Cargo.toml:12`) and `slug` (`:16`) are declared and never referenced: no `use`, no path, in `src`, `tests` or `examples`. Taking both out of a scratch copy builds all targets, and takes 23 crates out of the tree: `nalgebra`, `simba`, the `rand` family, `ab_glyph`, `ttf-parser`, `deunicode` and others. `ttf-parser` is one of the two `cargo audit` warnings (RUSTSEC-2026-0192, unmaintained).
- `image = "0.25"` (`Cargo.toml:12`) takes the default codecs: EXR, TIFF, HDR, QOI, TGA, DDS, ICO, PNM and others, and the AVIF encoder (`rav1e`). The program accepts `jpg`, `jpeg`, `png`, `gif`, `bmp` and `webp` by name, but decodes by content (`with_guessed_format`), so any of those codecs can be reached from a name that says `.png`: a PNM file named `p0001.png` converted without complaint. The `paste` crate, the other `cargo audit` warning (RUSTSEC-2024-0436), reaches the tree only through `exr`. With `default-features = false, features = ["jpeg", "png", "gif", "bmp", "webp"]` and the two unused crates removed, the tree went from 285 crates to 197, all targets compile and all 274 tests pass.
- The release build takes 5 min 13 s on an 8-core machine, and the binary is 6.9 MiB.

**Direction:** remove the two crates and restrict the image features. Pillow also sniffs content, so this is a smaller attack surface and a faster build, not a change to what is converted (the parity run is the check). A `cargo-deny` configuration (licenses, bans, advisories) would keep the tree from growing back.

### 12. The crates' own license notices are not shipped

**Class:** gap (not legal advice). **Priority:** Low to Medium. **Effort:** M.

**Where:** `THIRD-PARTY-NOTICES.md` covers KCC and Pillow and says of the crates: "they are listed in `Cargo.lock`, each under its own license"; the release archives hold the binary, `LICENSE-MIT`, `LICENSE-APACHE` and that file, and no `Cargo.lock`.

**Why it matters:** the binary statically contains 285 crates, among them 12 under BSD-3-Clause, 3 under BSD-2-Clause, 1 under NCSA and others, and these licenses ask that their copyright notices be reproduced with a binary distribution; MIT and Apache-2.0 ask the same of their notices. A pointer to a lockfile that is not in the archive is not that.

**Direction:** generate the list with the license texts at release time (`cargo-about` or `cargo-bundle-licenses`) and ship it in the archive beside `THIRD-PARTY-NOTICES.md`. Fewer crates (finding 11) means a shorter file.

### 13. CI and release hygiene

**Class:** gap. **Priority:** Medium for the first four rows, Low for the rest. **Effort:** S each, M together.

| Item | What was found |
|---|---|
| Floating toolchain | `dtolnay/rust-toolchain@stable` with `clippy -D warnings`: a new stable release can fail a pull request with no change in the repository. No `rust-version` in `Cargo.toml`, so no declared minimum. |
| Release is not gated on CI | `release.yml` runs on any `v*` tag, builds with `--locked`, and runs no test; a tag on a broken commit publishes. |
| Branch protection | `GET /branches/main/protection` returns 404: no required checks, force pushes are allowed. |
| No dependency or advisory checks | `ci.yml` has no `cargo audit` or `cargo deny`, and does not pass `--locked` to `clippy` or `test` (a lockfile that does not match `Cargo.toml` is accepted). There is no `dependabot.yml`, Dependabot security updates are disabled, and there is no `SECURITY.md`. |
| Actions are tags | `actions/checkout@v4`, `Swatinem/rust-cache@v2`, `actions/upload-artifact@v4`, `actions/download-artifact@v4`, not commits. |
| Artefacts | checksums are unsigned and live beside the binaries; no SBOM, no build provenance. |
| Platforms | Linux only as `x86_64` musl; no Linux `aarch64`, no Windows `aarch64`. The installer says "build from source instead" on an ARM Linux machine. |
| Installers | `install.sh` and `install.ps1` always take `releases/latest`, never read `checksums.txt`, and cannot install a given version. (They are in better shape than mangabind's: no JSON scraped with `grep`, `set -eu`, a `--version` smoke test at the end.) |

**Direction:** `rust-toolchain.toml` or a pinned version plus `rust-version`; `needs:` on a green CI run (or a tag only from a merged release PR, which is the habit already) and `cargo test` in the release job; `cargo audit`/`cargo deny` and `--locked` in CI; `dependabot.yml` and `SECURITY.md`; pin actions by commit. Branch protection is a setting, not a pull request. Build `aarch64` Linux if there are users on it. **Decision for the owner:** signing and provenance, as for mangabind.

### 14. The Linux binary is musl, and is slower than the same code on glibc

**Class:** gap. **Priority:** Low. **Effort:** S.

**Evidence:** the published `v0.7.2` archive (`x86_64-unknown-linux-musl`, static-pie, stripped) against a glibc build of the same commit, on one 180-page, 127 MiB volume, three alternating runs each, medians, on an 8-core machine:

```
default options                 glibc 14.4 s   musl 16.2 s   +12%
--upscale --forcepng            glibc 15.9 s   musl 17.4 s   +10%
--eraserainbow                  glibc 19.7 s   musl 28.5 s   +45%
```

The 180 pages are byte-identical between the two builds, so the difference is only the allocator and the C library (the two builds also used different compiler releases, so treat the figures as a bound, not a measurement of musl alone). The README sells "a single static binary", which is the reason for musl, and the cost is small for a conversion that takes seconds to a minute.

**Direction:** nothing to fix; a note in the README, and, if the eraser or the large-volume cases matter, a `mimalloc` or `jemalloc` global allocator for the musl target only. Linux `aarch64` (finding 13) would need the same choice.

## Findings — documentation, tests and structure

### 15. Documents that disagree with the code

**Class:** defect (documentation). **Priority:** Low. **Effort:** S.

- `docs/machine-protocol-v1.md` does not list `nested_toc_unsupported_format`, which the program emits (`mangapress x.cbz --nested-toc --format cbz --json-events` prints it, with `stage: configuration`). Every other code in the source is in the table, and every code in the table is in the source.
- ADR 0009 keeps its `Accepted` status and its original text, which still lists structured output as declined and says there is nothing to clean up on Ctrl-C. ADR 0011 does say that it supersedes the first conclusion ("not the rest of ADR 0009"), and 0010 and 0006 are marked superseded in the index, but 0009 has no pointer. Finding 3 is a second premise that has changed.
- `mangapress --help` has 54 options in one flat list (no `help_heading` is used), no example, no project URL and no exit codes; usage shows `[INPUT]` as optional although it is required unless `--list-profiles` or `--protocol-version` is given. The README does not say what the exit codes are or which stream carries what.

### 16. The parity check is manual, on one device, on a drawn corpus

**Class:** gap. **Priority:** Medium. **Effort:** M.

**Evidence:** the README of `tools/parity` says it is not part of `cargo test`, that it takes about five minutes, and that it should be run "when touching anything under `crates/mangapress-core/src` that changes pixels, and whenever KCC makes a release". There is no workflow that runs it, nothing that reminds anyone of a KCC release, and the scenarios use one device. Varying the device found a difference at once (finding 7), and none in the other 61 runs, so the pixel pipeline is in good shape and the weak spot is the per-device special cases that KCC keeps in `checkOptions`. The corpus is drawn by a program (real pages must not be committed), so it cannot show what real scans do; `--pages DIR` exists for that, and was not used here because no real pages were at hand.

**Direction:** make `PROFILE` an argument and run a short list (one old Kindle, one Scribe, one Kobo, one colour device, one reMarkable) in a scheduled workflow, against the pinned KCC tag, so that a pixel change is caught by the machine and a new KCC release is noticed by a weekly job that compares the latest tag with `REFERENCE_KCC`. Five minutes per device on a free runner is affordable once a week.

### 17. `run()` is a thousand-line function with failure state passed on the side

**Class:** gap. **Priority:** Low. **Effort:** L.

**Where:** `main.rs:481-1549` is one function of 1,068 lines inside a file of 1,912; it mutates a `&mut RunFailure` before each fallible step (`*failure = RunFailure::new(…)`) and relies on the caller to read it back.

**Why it matters:** a new fallible call placed after one of those assignments, and before the next, is reported under the wrong code with no compiler help. The `unknown_profile` value, for example, stays in `failure` after the profile has resolved (`main.rs:543-559`), through the checks that follow, until the `input_read_failed` assignment at `:643`; an error raised by a call added in between would be reported as an unknown profile. Nothing does that today; it is the shape in which mistakes are made while adding the next option.

**Direction:** not urgent. When the next large option lands, split the stages (inspect, plan, process, package, write) into functions that return a typed error carrying code, stage and context, and let `?` do the work.

### 18. The tests do not cover the hostile and the failing paths

**Class:** gap. **Priority:** Medium. **Effort:** M.

**Evidence:** 274 tests pass in about 80 s (244 in the core, 19 and 10 in the CLI's unit and protocol tests); coverage was not measured. There is no test of an archive with a lying size (finding 1), of an image above a size limit (2), of a write that fails or of an existing output (3), of two inputs with the same name (4), of a missing output folder (5), of a closed pipe in human mode (8), or of a symbolic link (9). The protocol tests already drive the real binary, so each of these needs a fixture and a few lines.

## What changes for mangabound

mangabound runs mangapress with `--json-events`, an output folder and a title per book, on a CBZ that mangabind wrote into a temporary workspace. That makes it exposed to finding 1 only through "convert only" on a loose CBZ the person chose (the abort has no event for the app to classify), to finding 2 in the same way (a page above Pillow's limit, a non-image entry that is large), and to finding 5 when a title is long (the failure arrives after the conversion, as `output_write_failed`). It is not exposed to findings 3, 6 and 8 in the way a terminal user is (it writes to a folder of its own, and reads the events), and to finding 4 only through two books with the same title. mangabound's unit test of the arguments, and its capability schema, are unaffected by any fix proposed here; fixes that add flags need a classification in `schemas/cli-capabilities.json` when the pin moves, and none of these adds one.

## Proposed order of work

One pull request per topic, each with its tests and, where it settles a question, an ADR. For each change in pixels, the parity check first. This is a proposal for triage, not a commitment.

1. **Inputs cannot hurt the process** (findings 1 and 2): no allocation from a declared size, no read of what the name already refuses, a ceiling per entry, Pillow's pixel limit. M, Medium.
2. **Output names and writes** (findings 3, 4, 5, 6): the name rule of `getOutputFilename`, `_kccN` for an existing default target, early checks, an atomic write. M, Medium. Needs the overwrite decision.
3. **Kindle DX CBZ** (finding 7, the device) with its parity scenario. S, Low.
4. **Dependencies** (finding 11): remove `imageproc` and `slug`, restrict `image`; then `cargo-deny`. S, Low-Medium. Re-run the full parity.
5. **CI, release and the parity workflow** (findings 13, 14, 16): pinned toolchain and actions, `--locked`, `cargo audit`, release gated, `dependabot.yml`, `SECURITY.md`, a weekly multi-profile parity job. M.
6. **Notices** (finding 12) once the tree is smaller. M.
7. **Small fixes** (findings 8, 10, 15): the dry-run pipe, the page number in the message, the protocol document, ADR 0009's pointer, help headings and an example. S.
8. **Hostile-input tests** (finding 18) go with each of the above, not as a separate pull request.
9. Findings 9 and 17 wait for a decision and for the next large option.

**Questions for the owner before work starts:** whether an explicit `--output file` may overwrite an existing file (finding 4); whether to apply mangabind's link rule to folder inputs (finding 9); where to draw the ceilings of finding 2, or whether to follow Pillow's exactly; whether `aarch64` Linux and signing are worth building (finding 13); and whether the weekly parity job is wanted (finding 16).
